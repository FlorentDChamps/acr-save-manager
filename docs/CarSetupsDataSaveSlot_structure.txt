================================================================================
BINARY STRUCTURE ANALYSIS : CarSetupsDataSaveSlot.sav
================================================================================
Game      : Assetto Corsa Rally
Engine    : Unreal Engine 5.4.3 (game 0.4)  /  5.6.1 (game 0.6)
Save class: /Script/dmengine.SaveGameSlot
Format    : GVAS (Unreal Engine Generic Save)
Encoding  : Little-Endian; strings = null-terminated with int32 length prefix
            (length INCLUDES the null terminator; length 0 = empty string,
             stored as 4 zero bytes with no content and no terminator)
            Unreal's FString rule, met in a 0.6 save on a setup named with
            an accent: a string that is not pure ASCII is written as
            UTF-16LE under a NEGATIVE length counting 2-byte code units,
            null included — "Été" = FC FF FF FF  C9 00 74 00 E9 00 00 00.
            A parser must never add a negative length to its cursor as a
            byte count.  ACR Save Manager writes names the same way, and a
            setup it renamed with accents loads in the game under that
            name (tested in game 0.6).

Reference files analysed:
  CarSetupsDataSaveSlot.sav        56 396 B   game 0.4, UE 5.4.3, 4 cars / 15 setups
  CarSetupsDataSaveSlot-0.6.sav   142 812 B   game 0.6, UE 5.6.1, 7 cars / 38 setups

4.1  BLOB HEADER
─────────────────────────────────────────────────────────────────────────────
  Field       Size   Type    Description
  ----------  -----  ------  ------------------------------------------------

─────────────────────────────────────────────────────────────────────────────
4.2  PER-CAR BLOCK  (repeated n_cars times)
─────────────────────────────────────────────────────────────────────────────

  Field           Size   Type       Description
  -------------   -----  ---------  -----------------------------------------
  car_name         var   FString    Car identifier, e.g. "AlpineA110"
  n_setups          4 B  int32      Number of setup entries that follow
  separator         4 B  int32      Separator token preceding entry[0]
  [layout]               ---        Entries are laid out as:
                                      separator (4 B)   ← the field above
                                      entry[0]
                                      separator (4 B)
                                      entry[1]
                                      …
                                      entry[n_setups-1]  ← NO trailing separator

SEPARATOR VALUE: not constant and not meaningful for parsing.  Observed 2 for
most blocks and 18 between two entries of HyundaiI20NRally2 in the 0.4 file
(the same block whose header separator field reads 2).  Parsers must skip these
4 bytes, never validate them.  When inserting an entry, reuse the value from the
target car block header.

CAR NAME CASE: car_name is an Unreal FName, compared without regard to case
and re-spelled by the engine on every save.  The same car is written both ways
across the samples, all from one player and one 0.4.0.86567 build:
"Hyundaii20NRally2" on 13/05 and 16/05, "HyundaiI20NRally2" on 14/05 and 18/05,
with the same setups (same names, same timestamps, same sizes) under both
spellings.  No file written by the game holds two blocks for one car, and inside
a block every entry's own car_name follows the block's spelling.  Parsers must
therefore match car_name case-insensitively, and never create a second block for
a car already present under another case.

NOTE: no "selected_idx" field exists anywhere in this file.
Confirmed by binary diff between two saves: one with the original setup selected,
one with a new "WIP" setup created AND selected.  The only changes were:
  • size_field updated (file grew)
  • n_setups for SkodaFabiaRSRally2 incremented (2 → 3)
  • new WIP entry + its preceding separator appended at end of Skoda block
No per-entry flag, no per-car flag, and no header field changed to reflect
the selection.

CONCLUSION: the active setup for each car is stored in PlayerDataSaveSlot.sav,
not here.  CarSetupsDataSaveSlot.sav is a pure setup definition store.

─────────────────────────────────────────────────────────────────────────────
4.3  PER-SETUP ENTRY  (variable size, no explicit size prefix)
─────────────────────────────────────────────────────────────────────────────

Entries are NOT prefixed by their own size.  Boundaries are implicit:
  • Within a car block, each entry is preceded by a separator (4 B)
    and followed by one if another entry comes after it.
    The final entry of each car block has NO trailing separator.
  • The car block ends when n_setups entries (+ n_setups-1 separators) have
    been consumed.
  • The last entry of the last car ends at EOF (= blob_start + 4 + size_field).

Locating entries without full parsing: search for the 5-byte marker
  [FF 01 00 00 00]  (int32 = 511 + byte = 0x00)
followed immediately by a valid FString (setup name).
Note: each marker is always preceded by the 4-byte separator of its car block
(or by the car block header for the first entry).

An entry is self-contained: exporting its raw bytes and re-inserting them into
another car block (or another save) is a valid operation, provided size_field
and n_setups / n_cars are updated.

─────────────────────────────────────────────────────────────────────────────
4.4  ENTRY HEADER FIELDS
─────────────────────────────────────────────────────────────────────────────

  # Field           Size   Type      Description
  - ──────────────  ─────  ────────  ─────────────────────────────────────
  1 entry_marker     4 B   int32     Constant : 511 (0x000001FF).
                                     Version or format flag; NOT a size.
  2 marker_pad       1 B   byte      Constant : 0x00
  3 setup_name       var   FString   User-defined setup name, e.g. "TAR1"
  4 author           var   FString   Author of the setup, e.g. "SomePlayer".
                                     EMPTY (int32 0, no bytes) in entries written
                                     by game 0.4; populated from game 0.5 onward.
                                     See §6.
  5 timestamp_lo     4 B   uint32    Low 32 bits of the creation / last-modified
  6 timestamp_hi     4 B   uint32    time, as .NET DateTime ticks, on the
                                     player's own clock — NOT UTC, unlike the
                                     other timestamps met in these saves
                                     (measured: an entry of a sample is stamped
                                     16 min before its file was written, which
                                     UTC ticks would put 1 h 44 after it)
  7 game_version     var   FString   Game build that wrote the entry,
                                     e.g. "0.4.0.85654", "0.6.0.100866"
  8 car_name         var   FString   Car identifier (same as car block name)
  9 track_name       var   FString   Stage/special identifier,
                                     e.g. "Saverne", "MonteCarloS2Sisteron"
  [conditions block] var   ---       See §4.5

WARNING (field 4): because an empty FString is exactly 4 zero bytes, a 0.4 entry
looks identical to an entry with an absent author.  Reading those 4 bytes as a
padding int32 — as parsers written against 0.4 files did — shifts every later
field by 4 bytes as soon as an entry carries a real author, and the timestamp
decodes to a nonsensical value.  Always read the field as an FString.

─────────────────────────────────────────────────────────────────────────────
4.5  CONDITIONS BLOCK  (immediately after track_name)
─────────────────────────────────────────────────────────────────────────────

The conditions block holds three lists of strings, in this order, each an
int32 count followed by that many FStrings:

  n_surfaces   4 B  int32
  surfaces[]   var  FString   e.g. "Tarmac", "Gravel", "Snow"
  n_weathers   4 B  int32
  weathers[]   var  FString   e.g. "Clear", "LightClouds", "HeavyRain"
  n_tags       4 B  int32
  tags[]       var  FString   game mode, e.g. "SingleStage_Tag", "RallyWeekend_Tag"
  → directly followed by kv_count (§4.6)

The counts are 0 or 1 in most entries, so the block often reads as flag +
optional string pairs: 12 bytes of zeros when nothing is stored, or
1, "Tarmac", 0, 0.  Earlier versions of this document read it that way and
took the tag count for an "unk_end" zero followed by unknown padding.  A
setup kept for several conditions lists them all: 5 weathers and 2 tags have
been measured on one entry, 1 to 3 on others.  Read every count and every
string; nothing in the block has a fixed size.

Measured: walked this way, every entry of every sample save and .setup file
ends exactly where the next one starts, and the last one exactly at the end
of the file — without scanning for kv_count.

IMPORTANT — surface not stored for every setup:
Binary inspection shows n_surfaces=0 on many setups even when the player picked
a surface in-game (e.g. Skoda on Monte Carlo, Hyundai on Wales gravel stages).
When n_surfaces=0 the surface is not present anywhere in this file — it is
either derived from the stage/track name at runtime or stored in
PlayerDataSaveSlot.sav.  This is unchanged in 0.6.

================================================================================
6. VERSION DIFFERENCES 0.4 → 0.6
================================================================================

  1. Engine: UE 5.4.3 → 5.6.1; UE5 package version 1012 → 1017;
     GVAS custom-version table 109 → 117 entries (+160 B).
     Everything after the header shifts by 160 bytes.

  2. Per-entry author FString (§4.4 field 4).  The field itself exists in 0.4
     files too, but always empty, which is why a parser that treated it as a
     4-byte zero padding worked until entries written by 0.5+ appeared.
     Entries observed with a populated author carry game_version 0.5.0.92585,
     0.5.0.94235 and 0.6.0.100866.

  3. No other structural change.  Blob header, car blocks, entry markers,
     conditions block and key-value pairs are byte-compatible; a .setup blob
     exported from a 0.4 save imports unchanged into a 0.6 save (its author
     field is simply empty).

  Verified by round-trip test: extract → rename → insert → remove restores the
  0.6 file byte-for-byte, with size_field / n_setups / n_cars consistent.
