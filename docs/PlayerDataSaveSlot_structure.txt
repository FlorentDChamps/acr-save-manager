================================================================================
BINARY STRUCTURE ANALYSIS : PlayerDataSaveSlot.sav
================================================================================
Game      : Assetto Corsa Rally
Engine    : Unreal Engine 5.4.3 (game 0.4)  /  5.6.1 (games 0.6 and 0.7)
Save class: /Script/dmengine.SaveGameSlot
Format    : GVAS (Unreal Engine Generic Save)
Encoding  : Little-Endian; strings = null-terminated with int32 length prefix
            (length INCLUDES the null terminator; length 0 = empty string,
             stored as 4 zero bytes with no content)
            Unreal's FString rule, not observed in these files (all ASCII):
            a string that is not pure ASCII is written as UTF-16LE under a
            NEGATIVE length counting 2-byte code units, null included.

Reference files analysed:
  PlayerDataSaveSlot_20260509_095118.bak   80 425 B   game 0.4, UE 5.4.3
  PlayerDataSaveSlot-0.6.sav              110 242 B   game 0.6, UE 5.6.1
  PlayerDataSaveSlot-0.7.sav              122 559 B   game 0.7, UE 5.6.1
--------------------------------------------------------------------------------

TABLE OF CONTENTS
  1. GVAS header
  2. Secondary header + property preamble
  3. PlayerSaveGameData block
     3.1  Player settings
     3.2  Vehicle and location inventory / roster
     3.3  Race event configuration (event configs)
     3.4  Stage, car and weather selection (after the event config list)

================================================================================
3. PlayerSaveGameData BLOCK
================================================================================

Root structure (0x09ED in 0.4, 0x0AB5 in 0.6) :
  int32  size_field_1    // 77 880 (0.4) / 107 497 (0.6)
  int32  size_field_2    // 87 (0x57) in both versions
  [custom binary data — see the sections below]

INVARIANT VERIFIED in both versions:
  size_field_1 == file_size - (offset_of_size_field_1 + 4)
Inserting or removing bytes anywhere in the block must update that field (which
is what ACR Save Manager does when it writes an event config block back).  There
is no checksum of any kind.

--------------------------------------------------------------------------------
3.2  VEHICLE AND LOCATION INVENTORY / ROSTER
--------------------------------------------------------------------------------

Right before the event config list (§3.3) sit two lists of the same shape: a run
of elements { FString name ; int64 ticks } — the int64 being a .NET timestamp
(UTC), most likely an unlock or last-used date.  The location list is preceded
by its own int32 counter:

  locations 0.4 : count = 2   -> "Wales", "Alsace"
  locations 0.6 : count = 4   -> "Wales", "Alsace", "MonteCarlo", "Greece"

The cars appear just before, in the same shape (VWPoloGTIR5,
LanciaRally037Evo2, SkodaFabiaRSRally2, ...), behind their own int32 counter:
17 cars in every 0.7 save seen (2026-11-22), where the catalog lists 20 — the
Alpine A110 and both Lancia Delta S4 are missing, the Alpine although the
per-car detail further up names it.  ACR Save Manager finds this list from
the event list backwards (locations, then cars, each ending where the next
starts) and uses its spellings for the car it writes (§3.4).  The per-car
detail (upgrade levels, stats) was not re-validated on 0.6 and remains to be
confirmed.

The location counter sits immediately before the first location name, and the
list is immediately followed by the event config counter (§3.3).

--------------------------------------------------------------------------------
3.3  RACE EVENT CONFIGURATION (event configs)
--------------------------------------------------------------------------------

List PREFIXED BY ITS COUNTER (int32) :
  n_events   4 B   int32    4 in 0.4 (offset 0x16E9) / 5 in 0.6 (offset 0x16E1)
                            1 in a new player's save (0.6.0.100866): DefaultRally
                            only, the list holding just the modes played
  [n_events] × EventConfig

EventConfig structure:
  event_name      var   FString   e.g. "DefaultRally"
  n_contexts       4 B  int32     1 in every save analysed; 2 with a rally
                                  weekend in progress (see below)
  [n_contexts] × Context :
    class_path    var   FString   "ERaceEventSerializableContext::RaceEventSettings"
                                  (len=49 — this is NOT a "/Script/..." path)
    nb_versions    4 B  int32     0, 1 or 2
    [nb_versions] × { UUID 16 B ; int32 version }
                                  the same shape as the GVAS custom version
                                  table (§1)
    n_components   4 B  int32     1 in a RaceEventSettings context
    [n_components] × Component :
      comp_name   var   FString   e.g. "RaceEventRaceSettingsRallyWeekendComponent"
      data_size    4 B  int32     size of the data that follows
      data   data_size B bytes    component data (the Rally Weekend's: below)

  The byte count is the one an earlier version of this document gave
  (nb_uuids × 16 B, then nb_uuids + 1 int32): each UUID is followed by its
  version, and the last int32 is the number of components.  Checked on a 0.6
  save (game 0.6.0.100866), DefaultRally:
    02 00 00 00                                       nb_versions = 2
    37900b75-a349-43cf-23b4-e9af80aeb550  01 00 00 00 version 1
    e661814c-7041-89aa-eb01-75a111411909  02 00 00 00 version 2
    01 00 00 00                                       n_components = 1

  A RALLY WEEKEND IN PROGRESS (not seen in the saves analysed here; layout
  from ACR Daily's decoding, see the sources at the end): the game keeps the
  rally between sessions as a second context of DefaultRally, right after the
  settings one, and removes it when the rally ends (last stage finished or
  retired from):
    class_path    "ERaceEventSerializableContext::RaceEventState"
    nb_versions   0
    n_components  4   (the rally under way; not decoded here)
  ACR Save Manager reads every context and component, and marks a
  DefaultRally holding this context as a rally in progress: the event is
  shown, but never written over (the rally under way travels in the same
  block as the settings).

Events and components observed:

  0.4 (n_events = 4)                    data_size   nb_versions
  --------------------------------------  ---------   --------
  DefaultFreePractice  -> ...FreePracticeComponent  72       1
  DefaultTimeAttack    -> ...TimeAttackComponent   118       1
  DefaultSingleStage   -> ...SingleEventComponent   96       1
  DefaultRally         -> ...RallyWeekendComponent var       2

  0.6 (n_events = 5) : the same, plus
  DefaultOnlineSingleStage -> ...SingleEventComponent 73      2

  0.7 (n_events = 6 once the online Rally Weekend has been set up), plus
  DefaultOnlineRally   -> ...RallyWeekendComponent var       3

A block starts at the length prefix of its event_name and ends exactly where
the next event config starts.  Measured sizes:

  DefaultRally         1 567 B in 0.4 (AlsaceWeekendLong)
                         618 B in 0.6 (MontecarloWeekendShort)
  DefaultTimeAttack      274 B in both versions
  DefaultFreePractice    232 B in both versions

Only DefaultRally names its configuration inside its blob (see below); the
others hold numeric settings only — no block names a stage or a car.

RallyWeekendComponent data, DefaultRally (offline) and DefaultOnlineRally
(online).  Offsets from the start of the data.  The fields are the game's own
(its classes URaceEventRaceSettingsComponent, URaceEventRaceSettingsRally-
Component and URaceEventRaceSettingsRallyWeekendComponent, and the structures
they hold), in the order the save writes them, which is not always the order
the game declares them in.  Each field was checked on 0.7.0.109370 saves, by
changing one menu setting at a time.  A flag ("bool") takes 4 bytes, 0 or 1;
an enumeration takes 1 byte, the number the game gives its value (the names:
the catalog's "options", see the README).

  +0x00   bool     bTyresConsumption        not in the menus yet (0.7)
  +0x04   u8       TyresDamage              not in the menus yet
  +0x05   u8       ManualRespawn            0 off, 1 on, 2 realistic
  +0x06   bool     bFuelConsumption         not in the menus yet
  +0x0A   bool     bDamagesEnabled          car damage
  +0x0E   bool     bGraphicalDamages        graphical damage
  +0x12   u8       Collisions               damage intensity  } 0 off, 1 light,
  +0x13   u8       Wear                     wear intensity    } 2 severe,
  +0x14   u8       MechanicalFailures                         } 3 realistic
  +0x15   42 B     WeatherOptions           of the stage to be driven next
                                            (below)
  +0x3F   bool     bHardCore                hardcore mode: forces both damage
                                            flags on and the realistic penalty

  OFFLINE (DefaultRally), the opponents then the running order:
  +0x43   int32    NumOfOpponents           30 in a new player's save
  +0x47   float32  Skill                    0.5 .. 1.2, shown x100
  +0x4B   u8       Consistency              0 realistic, 1 very low, 2 low,
                                            3 high
  +0x4C   u8       Spread                   0 realistic, 1 competitive
  +0x4D   float32  RaceCraft                0.1, locked in the menu
  +0x51   u8       CarClassSelection.Type   0 automatic, 1 same class, 2 same
                                            car, 3 custom
  +0x52   int32    n_slots                  then n_slots × u8: the custom
                                            selection, empty in every save
                                            (no menu fills it in 0.7)
  +0x56   u8       RacePenalty              0 off, 1 light, 2 realistic
  +0x57   u8       RunningOrderType         0 random, 1 custom
  +0x58   int32    RunningOrder             start position, 1 = first on the
                                            road
  +0x5C   float32  its random roll
  +0x60   the calendar (below)

  ONLINE (DefaultOnlineRally), no opponents and no running order but the
  lobby:
  +0x43   u8       RacePenalty
  +0x44   int32    MaxPlayers               2 .. 16
  +0x48   u8       CarSelectionOption       0 any car, 1 same class, 2 same car
  +0x49   the calendar (below)

  The offsets past +0x52 hold with no custom slots: an offline calendar
  starts at +0x60 + n_slots.  The online one's context carries a third
  version, 570b1309-a241-5e0e-92e3-6b8ec7b8d429 (version 1), which is what
  tells the two layouts apart besides the event name; ACR Save Manager reads
  the data as the offline layout, then as the online one, and keeps the one
  that ends exactly on the last byte.

  The calendar, FRallyWeekendCalendar:
          FString  CalendarPresetId          the game's calendar it started
                                             from, e.g. "MontecarloWeekendShort"
                                             (the location, then Short / Medium
                                             / Long for the 1, 2 and 3-day ones)
          int32    n_stages
          [n_stages] × FRallyWeekendSubEvent {
            int32    Day                     0 = day 1
            FString  TrackId                 the stage, e.g.
                                             "MonteCarloS2SisteronCut2Reverse"
            42 B     WeatherOptions          as set for that stage
            42 B     DefaultWeatherOptions   what the menu's RESET goes back to
            FString  PreRaceZoneConfigurationId
                                             the zone before the stage:
                                             "ServiceParkDefault" (60 min),
                                             "ServiceParkShort" (30 min) and
                                             "ServiceParkLong" (90 min, both
                                             new in 0.7), or "NoZone"; every
                                             day starts with a service park
          }
          FString  CustomPresetName          empty in every save seen
          bool     bIsCustomPreset           1 once the calendar was changed in
                                             the menu
          16 B     CalendarInstanceId        a GUID, the same in the offline
                                             and the online weekend of a save

  The game's own calendars (stages, start times, service parks) are the
  catalog's "rallyCalendars".  An earlier version of this document read
  "int32 n_stages, int32 0": that 0 is the first stage's day.

  Writing a Rally Weekend (ACR Save Manager's editor; a weekend written with
  several settings changed loads in game 0.7, tested 2026-11-22): the
  component data is rebuilt field by field, its data_size and size_field_1 are fixed up, and
  nothing else in the file moves.  The weather of the stage to be driven next
  (+0x15) is the first stage's, CalendarInstanceId is kept, bIsCustomPreset is
  set unless the calendar is still one of the game's as it loads, and a stage
  picked from the catalog is written under the catalog's id, in lowercase
  (TrackId is an FName, looked up without regard to case: a stage written so
  loads in game 0.7, tested 2026-11-22).  The game must be closed: it keeps
  the save in memory, writes it as soon as a menu setting changes, and does
  not read it again while it runs.

  The same settings go into either weekend: the app's rallies hold the
  opponents, the running order and the lobby together, and each weekend takes
  its own layout (offline: AIOptions, penalty, running order; online: penalty,
  MaxPlayers, CarSelectionOption).  What no menu shows stays the weekend's
  own: the tyre and fuel options, the AI's custom car slots, CustomPresetName
  (empty in every save seen, a changed calendar included) and
  CalendarInstanceId.

The other components (FreePractice, TimeAttack, SingleEvent) share the same
prefix, +0x00 to +0x42: the race options, the weather at +0x15 and hardcore

  SingleEvent (DefaultSingleStage, DefaultOnlineSingleStage)
                URaceEventRaceSettingsSingleEventComponent adds no field to

So each block carries its own rules, weather and start time, the Rally Weekend
one weather block per stage besides; §3.4 holds the stage the single-stage
modes share, with three of its weather options.

--------------------------------------------------------------------------------
3.4  STAGE, CAR AND WEATHER SELECTION (after the event config list)
--------------------------------------------------------------------------------

Immediately after the last event config comes a short section that belongs to
no block: the last stage used, the car, and three weather options.  The JSON
export calls it "weather_settings".  Observed in game 0.7 (2026-11-22), one
menu changed between two saves:

  - Single Stage offline or online, Free Practice: picking a stage writes it
    here, and the mode's weather type, start time and time speed with it (the
    Free Practice wrote its stage and start time, its weather type not).
  - Opening a Rally Weekend put a weekend's first stage here.
  - A Single Stage, opened again, copies the weather type, start time and
    time speed found here into its own block (with new random draws), and
    keeps the rest of its block: wetness, snow, grip, forecast, opponents.

So the single-stage modes share one stage, the one shown last.  ACR Save
Manager writes a rally's first stage into the Single Stage blocks, the Free
Practice block and this section together, so that they agree (loaded by game
0.7, tested 2026-11-22).

  stage        var  FString   e.g. "GreeceS3ElatiaCut2Forward"
  car          var  FString   e.g. "SkodaFabiaRSRally2"
  n_options     4 B int32     3 in both versions; 0 in a new player's save
                              (no single stage driven yet)
  [n_options] × { FString path ; FString value } :
    "/Script/acr.WeatherOptions/StartingTime"
        -> "(TimeSeconds=30600.000000)"
    "/Script/acr.WeatherOptions/Preset"
        -> "(WeatherType=WT_LIGHT_CLOUDS,RandomUniform=0.963836,bRandom=False)"
    "/Script/acr.WeatherOptions/TimeSpeed"
        -> "WT_SPEEDREALISTIC"

  The options come in no fixed order: another 0.6 save lists Preset first,
  then StartingTime and TimeSpeed.  Read them by their path, never by rank.

  Measured: the event config list ends at 0x2004 (0.4) and 0x1D48 (0.6), while
  the first option path starts at 0x203D and 0x1D85 — outside every block.

  It is not the rally weekend's weather either: in 0.6 the stage named here is
  GreeceS3ElatiaCut2Forward while the weekend blob names
  MonteCarloS2SisteronCut2Reverse.

  The car is one for every mode: the one the menus show until another is
  picked.  ACR Save Manager rewrites it alone (the FString in place, then
  size_field_1), the stage and options untouched; a car the list of §3.2
  names keeps that spelling, another goes under the catalog's id.

  Writing it (ACR Save Manager): the stage, the car kept, then the options in
  the save's own order, each value spelled as the game spells it — the
  numbers with six decimals, the weather type and time speed by the game's
  enumerators (WT_LIGHT_RAIN, WT_SPEEDREALISTIC), bRandom as True or False.
  A save with no option yet (a new player's) gets all three.

  Consequence for §3.3: a block copied alone stops at the end of that
  block, so none of this travels with it.  The list and this section are
  contiguous, from n_events to the last option value.

================================================================================
4. LOCATING SECTIONS WITHOUT HARD-CODED OFFSETS
================================================================================

Offsets move with every game version, and event names change (0.6 added
DefaultOnlineSingleStage).  ACR Save Manager uses two methods, both
independent of the version:

  1. String anchoring, for the one field named in a stable way:
     * "PlayerSaveGameData\0"  -> size_field_1, right after the FString

     ATTENTION: an event name appears up to twice in the file — once as the
     event config (§3.3), once inside another block that reuses the name, the
     other occurrence holding different fields after it.  Anchoring an event
     config on its name alone lands on the wrong one; the tool finds the whole
     list by method 2 instead.

  2. Structural validation, for the lists whose names vary:
     the section is parsed at every candidate offset and the first one that
     decodes completely is kept (consistent counter, printable null-terminated
     ASCII FStrings, plausible bounds on the counters).  That is how the event
     config list (§3.3) is located, without a single hard-coded name.
     The stage, car and weather selection (§3.4) is then read forward from
     the end of that list: none of its option paths comes first in every
     save, so none can anchor it.

     Plausibility bounds used by the scanner:
       n_events 1..64 ; n_contexts 1..8 ; nb_versions 0..8 ;
       n_components 1..8 ; data_size 0..500 000 ; n_options 0..10
       FString length 1..2000
       identifiers: 3..64 characters, [A-Za-z][A-Za-z0-9_]*
       every context's class path starts with
       "ERaceEventSerializableContext::" — what keeps a list of one event
       from being found by chance

================================================================================
5. DIFFERENCES 0.4 -> 0.6, 0.6 -> 0.7
================================================================================

  1. Engine: UE 5.4.3 -> 5.6.1; package UE5 version 1012 -> 1017; custom version
     table 109 -> 117 entries (+160 B).  Everything after the header shifts by
     160 bytes.
  2. Secondary customs: 12 -> 14 entries (+40 B).
  3. A fifth event config: DefaultOnlineSingleStage.
  4. A new country: Greece (locations 2 -> 4 with MonteCarlo and Greece).
  5. NO structural change: the GVAS header, the event configs and the
     size_field_1 invariant are identical.  The reading problems met on the
     0.6 files came from wrong assumptions already present for 0.4

================================================================================
6. NOTES FOR MODIFICATION
================================================================================

1. STRINGS (FString)
   - Always preceded by a little-endian int32 giving the length WITH the
     trailing \0
   - e.g. "French" = 07 00 00 00 + 46 72 65 6e 63 68 00
   - Length 0 = empty string (4 zero bytes, no content)
   - A negative length means UTF-16LE and counts 2-byte code units (see the
     encoding note at the top)
   - When you change a string, update its length prefix TOO

2. FLOATS
   - IEEE 754 float32 little-endian; durations are in SECONDS (e.g. 114.795)
   - In Python: struct.pack('<f', seconds)

3. INTEGERS
   - All signed little-endian int32 unless stated otherwise
   - Counters must stay consistent with the number of entries that follow

4. TIMESTAMPS
   - int64 little-endian = .NET ticks (100 ns since 0001-01-01), in UTC
   - Present in the car / location lists

5. UUIDS
   - 16 raw bytes (no dashes); do not touch the ones in the GVAS header

6. FILE SIZE
   - No CRC and no signature: the game trusts the content
   - BUT size_field_1 must always equal file_size - (offset + 4)

import struct

def read_fstring(data, off):
    l = struct.unpack_from('<i', data, off)[0]
    if l == 0:
        return '', off + 4                      # empty string
    if l < 0:                                   # UTF-16LE, -l code units
        n = -l * 2
        return data[off+4:off+4+n-2].decode('utf-16-le'), off + 4 + n
    if l > 4096:
        return None, off
    s = data[off+4:off+4+l-1].decode('utf-8', errors='replace')
    return s, off + 4 + l

def write_fstring(s):
    if s == '':
        return struct.pack('<i', 0)
    if any(ord(c) > 0x7f for c in s):           # not pure ASCII: UTF-16LE
        b = (s + '\x00').encode('utf-16-le')
        return struct.pack('<i', -(len(s) + 1)) + b
    b = s.encode('ascii') + b'\x00'
    return struct.pack('<i', len(b)) + b

def read_ticks(data, off):
    ticks = struct.unpack_from('<q', data, off)[0]
    return ticks, off + 8                       # .NET UTC ticks
